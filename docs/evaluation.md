# Замеры base и SFT

## Пересчёт сохранённых предсказаний

Оценщик v3 обработал все 15 905 сохранённых ответов пяти конфигураций, по 1034 на Spider dev и по 2147 на Spider 1.0 test. Для обоих наборов сверили порядок вопросов, `db_id` и эталонный SQL с исходным Spider. Переобучение и новая генерация для этого пересчёта не выполнялись. Исходные JSONL и метрики доступны в [коммите 673d902](https://github.com/Pavel-V418/BaseModel-vs-SFT/tree/673d90294d93bce27c549604e52c5cc1558bcb26/results). В [JSON аудита](../results/evaluation_review.json) перечислены изменившиеся поля, метрики до и после пересчёта и версии оценщиков.

- В `wta_1` SQLite возвращала ошибку декодирования `last_name` для двух эталонных запросов dev. Декодирование через UTF-8 с `surrogateescape` сохраняет различия между повреждёнными значениями TEXT и между TEXT и BLOB. Проектная Execution Accuracy выросла на один правильный ответ у Base zero-shot и на два у каждой из остальных четырёх конфигураций dev.
- Парсер учитывает строковые литералы, quoted identifiers, комментарии и вложенные запросы. На двух выборках изменились четыре значения `pred_sql`, остальные флаги у этих четырёх строк совпали.
- На test проектная Execution Accuracy всех конфигураций совпала с исходной. На Windows один запрос Base 4-shot, `test_0447`, превысил пятисекундный лимит. Он успевал выполниться в Colab, поэтому Valid SQL изменился с 46,16% до 46,11%. Новый пересчёт выполнен на SQLite 3.50.4.

## Сравнение с реализациями Spider

**Проектная Execution Accuracy** сравнивает результаты на одной исходной SQLite-базе, сохраняет дубликаты и округляет вещественные значения. **Текстовый Exact Match** сравнивает SQL после нормализации регистра и пробелов. **Spider legacy Execution Accuracy** использует `eval_exec_match` из первоначального оценщика Spider, коммит `b7b5b8c`. Он сопоставляет столбцы по разобранным компонентам SQL и сравнивает последовательности значений. Предикт, который не удалось разобрать, получает ноль по legacy execution. Выполнение настроено только на чтение, с тем же таймаутом и обработкой UTF-8, что и в проектном оценщике. [Исходный оценщик Spider](https://github.com/taoyds/spider/blob/b7b5b8c890cd30e35427348bb9eb8c6d1350ca7c/evaluation.py)

**Официальный Exact Match** выполнен через `Evaluator.eval_exact_match` из `test-suite-sql-eval`, коммит `e97acc5`. Он сопоставляет структуру SQL по частям запроса, применяет карты внешних ключей и игнорирует значения и DISTINCT в структурном сравнении при настройках по умолчанию. Поэтому отличающийся текст может получить зачёт, а одинаковый текст, который парсер Spider не смог разобрать, — ноль. Оба оценщика разобрали все эталонные SQL на dev и test. [Официальная реализация](https://github.com/taoyds/test-suite-sql-eval/blob/e97acc546ecbee8fa27fa8dbf025ef61493a876c/evaluation.py)

**Test Suite Accuracy** — метрика исполнения лидерборда Spider с дополнительными SQLite-базами. Её значение не рассчитано. Официальный архив этих баз вернул сообщение об исчерпании лимита скачиваний Google Drive. В таблицах приведена legacy Execution Accuracy на исходных базах. [Протокол Spider](https://yale-lily.github.io/spider/) · [Архив дополнительных баз](https://drive.google.com/file/d/1mkCx2GOFIqNesD4y8TDAO1yX1QZORP5w/view)

## Проверка Base 4-shot

Промпт измерен токенизатором той же ревизии Qwen2.5-0.5B. Четыре примера добавили 768 токенов. На test длина без примеров составила 61–606 токенов, медиана 153. С примерами — 829–1374, медиана 921. С учётом 256 токенов генерации все входы помещались в контекст модели в 32 768 токенов.

На test до лимита завершились 29 из 2147 генераций, Stop Rate — 1,35%. Среди ответов без раннего EOS 982 содержали SQL, который выполнился при пересчёте. Проверили реальные ответы из [JSONL Base 4-shot](../results/spider_test/base_0.5b_few_eval.jsonl).

- `test_0001` продолжил выдавать схемы после готового `SELECT COUNT(*) FROM club;`. Парсер извлёк законченный SQL, результат совпал с эталоном.
- `test_0005` дошёл до лимита на длинной цепочке JOIN. Извлечённый SQL не выполнился.
- `test_0016` завершился до лимита, но вернул SQL с некорректными ссылками на колонки. EOS сам по себе не подтверждает корректность SQL.

С этими четырьмя демонстрационными примерами, базовой Qwen2.5-0.5B и указанными настройками проектная Execution Accuracy на test составила 18,07% против 22,08% у zero-shot. Этот вывод относится к проверенной конфигурации Base 4-shot.

## Воспроизводимость

- **Spider dev, 1034 вопроса.** В двух первоначальных полных генерациях Base zero-shot и исходного SFT совпали сохранённые ответы. В v3 повторно проверен SQL всех сохранённых ответов пяти конфигураций.
- **Spider 1.0 test, 2147 вопросов.** У каждой из пяти конфигураций есть полный набор ответов. В v3 повторно проверен SQL по всем вопросам. Две независимые генерации для проверки воспроизводимости Base zero-shot и исходного SFT охватывали первые 16 вопросов. Их ответы совпали с соответствующими строками полных прогонов.
- **Тесты.** `pytest` — 43 прошли, включая проверку сложности по исходному скрипту Spider. Добавлены регрессии для некорректного UTF-8, строк, комментариев, вложенных запросов и повторного запуска с выбранным каталогом SQLite.

Для одинаковой оценки 0.5B, 1.5B и 3B используется `src.evaluate` версии 3. Пример повторной оценки сохранённых ответов на подготовленном test:

~~~bash
python -m src.evaluate --model Qwen/Qwen2.5-0.5B --spider-dir data/spider-test \
  --data data/spider-test/test.jsonl --predictions results/spider_test/base_0.5b_zero_eval.jsonl \
  --mode zero --run_name base_0.5b_zero_v3 --results_dir /tmp/spider-v3
~~~

Подготовить каталог test можно через `python -m src.spider_test --archive data/spider_data.zip --data-dir data/spider-test --prepare-only`. Для dev используется `--spider-dir data/spider --data data/test.jsonl`. Для Base 4-shot укажите `--mode few --fewshot` с файлом четырёх примеров.

Скрипт `scripts/score_spider_official.py` сравнивает те же сохранённые ответы с заданным upstream checkout. Зависимости для официальной оценки — `nltk==3.9.2`, `sqlparse`, `tqdm`, ресурсы NLTK `punkt` и `punkt_tab`. Для структурной оценки укажите путь к `test-suite-sql-eval` на коммите `e97acc5`. Для legacy замените параметр на `--protocol legacy --evaluator /path/to/spider` с коммитом `b7b5b8c`. Режим `--suite-dir` требует дополнительных баз для каждого `db_id`.

~~~bash
python -m scripts.score_spider_official --protocol test-suite --evaluator /path/to/test-suite-sql-eval \
  --spider-dir data/spider-test --data data/spider-test/test.jsonl \
  --predictions results/spider_test/base_0.5b_zero_eval.jsonl --output /tmp/spider-official.json
~~~

### Одинаковая процедура

Один подготовленный test.jsonl и одинаковые русские prompt (схема, вопрос, SQL:), без chat template и без few-shot примеров. Общий src.evaluate вызывает load_model из src.utils; для SFT меняется только adapter. Генерация: do_sample=False, num_beams=1, max_new_tokens=256, batch=16, tokenizer.padding_side='left', seed=42. В исходной конфигурации измеренной Qwen eos_token_id=151643, num_beams по умолчанию равен 1. Версии окружения измерения сохранены в results/environment_colab.json и results/requirements-colab-measured.txt.

extract_sql берёт SQL из блока sql, если он есть, затем обрезает по первому разделителю ;, пустой строке, Вопрос: или <|endoftext|>. Запросы выполняются отдельно на SQLite, открытой через URI mode=ro. Authorizer разрешает чтение и запрещает изменения, ATTACH, VACUUM и административные операции; пустые ответы не считаются валидными. Progress handler прерывает запрос примерно через 5 секунд. Временные таблицы сортировки остаются в памяти.

Сравнение результатов сохраняет дубликаты; порядок строк учитывается, если в gold SQL есть ORDER BY. Вещественные числа округляются до 6 знаков, целые и BLOB сохраняются без потери точности. Exact match — схлопывание пробелов, удаление конечной точки с запятой и сравнение без учёта регистра; это не семантическая эквивалентность SQL. Stop rate — EOS встретился до последнего из 256 разрешённых токенов.

### Проверка сохранённых результатов

Архивы 20261117_145842_results.zip и 20261117_152306_results.zip содержат по одному полному base/SFT прогону и повторные smoke проверки на 16 примерах. Полные JSONL для каждой модели совпали побайтово между двумя архивами. В Git сохранена одна копия каждого полного результата.

При аудите исправлены обработка пустого SQL, ограничения SQLite, точность чисел/BLOB и выбор EOS. Все 2068 сохранённых ответов повторно выполнены исправленным evaluator (evaluation_version=2); ни одна строка флагов и ни одна метрика не изменились. Это повторная проверка сохранённых генераций без нового model inference. Новые хеши JSONL отличаются от исходных из-за сериализации/переводов строк; хеши обоих вариантов и архивов указаны в results/evaluation_manifest.json. Идентификаторы сохранены из измеренного test.jsonl; свежая подготовка данных после изменений master может дать новые строковые id и другой SHA.

Для независимой проверки с тем же внешним пакетом:

~~~bash
python -m src.evaluate --model Qwen/Qwen2.5-0.5B --predictions results/base_0.5b_zero_eval.jsonl --mode zero --run_name verify_base --results_dir /tmp/verify_eval
python -m src.evaluate --model Qwen/Qwen2.5-0.5B --adapter outputs/sft_0.5b_nall_r16_lr1e-4_s42/final --predictions results/sft_0.5b_zero_eval.jsonl --mode zero --run_name verify_sft --results_dir /tmp/verify_eval
~~~

Скрипт проверяет число записей, id, question и gold_sql перед повторной оценкой. --predictions не загружает модель; нужны JSONL данных и SQLite-базы. Итоговые overall и by_difficulty должны совпасть с опубликованными.

### Новый запуск на GPU

Открыть notebooks/colab_gpu.ipynb в Colab, выбрать T4 GPU и выполнить Run all. Ноутбук загружает исходники из ветки participant-2/evaluation; для фиксированной версии указать SHA коммита в REPO_REF. Код и вывод не требуют локального CPU inference. RUN_TRAINING=False оставляет готовый адаптер; True запускает новое обучение и создаёт новый эксперимент.

Для точного набора данных нужен внешний basemodel_colab_bundle.zip (116789255 байт; SHA-256 в manifest). Он уже передан участникам проекта; публичной ссылки на него в репозитории нет. Загрузить его через Files → Upload to session storage в /content. Альтернатива — две части .part001/.part002 в MyDrive/BaseModel-vs-SFT-Colab. Ноутбук проверяет SHA и извлекает только data/ и outputs/, сохраняя исходники из Git. Веса base скачиваются из Hugging Face. Результаты записываются на Drive, если он подключён, либо скачиваются последней ячейкой в ZIP; локальные файлы Colab исчезают после удаления среды.

Без этого пакета можно подготовить новый набор из официального Spider: см. scripts/download_spider.sh, затем python -m src.data --spider_dir data/spider --out_dir data --val_size 400 --seed 42. Текущий master добавляет id и нормализует вопрос, поэтому для сопоставления с историческим измерением необходимо сверить данные; считать такой запуск новым экспериментом. Готовый LoRA отдельно поставляется в results_sft_0.5b_nall_r16_lr1e-4_s42.zip, папка outputs/.../final. Хеш весов в manifest. Новое обучение не гарантирует побайтового совпадения адаптера.

Обычные команды генерации:

~~~bash
python -m src.evaluate --model Qwen/Qwen2.5-0.5B --mode zero --run_name base_0.5b_zero
python -m src.evaluate --model Qwen/Qwen2.5-0.5B --adapter outputs/sft_0.5b_nall_r16_lr1e-4_s42/final --mode zero --run_name sft_0.5b_zero
~~~

Для короткой проверки добавить --limit 16; для few-shot — --mode few. Каждый запуск создаёт <run_name>_eval.jsonl и <run_name>_eval_metrics.json. Few-shot и модели другого размера этими результатами не покрыты.

### Что опубликовано и что осталось внешним

В Git входят evaluator, parser, тесты, чистый Colab ноутбук, зависимости, полный результат по каждому примеру, сводные метрики, версия окружения, контрольные суммы и небольшие отчёты обучения. Данные Spider, SQLite, ZIP, LoRA и базовые веса остаются внешними файлами.

BaseModel-vs-SFT-export.zip — резервная копия: исходники/данные совпадают с исходным bundle, дополнительно вложены оба каталога результатов. Отдельно публиковать его содержимое целиком не нужно. Архивы *_results.zip — подтверждение двух запусков. Присланный выполненный .ipynb содержит выводы этих запусков; в Git сохранена очищенная версия с подготовкой исправленных исходников.
